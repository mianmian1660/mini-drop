# 周期采样产品定位：定时深度诊断

> 本文定义周期性采样（Periodic Deep Sampling）在整个 Mini-Drop 中的产品定位，并对照当前代码实现，给出差距清单与落地路径。

## 1. 产品定位（一句话）

周期性采样不是一种独立采集引擎，也不是简化版持续采集，而是**「定时执行的高保真深度诊断」**。它与单次采样共用采集器、任务执行、产物和分析链路，只是触发方式不同。

## 2. 一句话区分三种形态

| 形态 | 场景 | 一句话 |
|---|---|---|
| 单次采样 | 问题正在发生，现在诊断 | 立即诊断 |
| 周期性采样 | 问题会在已知时段反复发生，自动诊断 | 定时诊断 |
| 持续采集 | 不知道问题何时发生，持续覆盖和回溯 | 持续观测 |

## 3. 在项目中的结构

整个系统呈现为两个核心能力，周期性采样归属于「深度诊断」而非与单次、持续并列成三套引擎：

```text
持续观测
负责：长期覆盖、趋势、回溯、发现异常
        │
        │ 发现异常后可触发
        ▼
深度诊断
├── 立即执行：单次采样
└── 定时执行：周期性采样
```

## 4. 它应该解决的问题

最适合以下场景：

- 每天固定时间出现业务高峰
- 定时批处理、数据同步、备份任务
- 周期性 Java GC、内存分配或锁等待问题
- 发布后定期检查性能是否回归
- 希望在同一业务阶段反复获得可比较的火焰图
- 持续采集发现大致异常时段后，需要定时进行更深诊断

它回答的核心问题：

> 在一个可预测、重复出现的业务窗口里，程序内部的热点和调用路径发生了什么变化？

## 5. 它应该产生什么效果

每次计划触发，都应生成一个独立、完整的深度诊断窗口：

```text
周期计划
├── 10:00 诊断窗口
│   ├── 完整火焰图/直方图
│   ├── TopN 热点
│   ├── 原始采集产物
│   └── 分析结论
├── 10:05 诊断窗口
├── 10:10 诊断窗口
└── 10:15 诊断窗口
```

用户进入计划详情后，首先看到：

- 执行时间轴
- 每个窗口的成功、失败和采集质量
- CPU、IO、调度延迟等趋势
- 与基线相比的热点变化
- 新出现或明显变热的函数
- 可进入每个窗口查看完整诊断报告

理想效果不是「积累了一堆重复任务」，而是：

> 自动建立一组条件一致、时间有序、可以相互比较的性能快照。

## 6. 「深度」具体体现在哪里

周期性采样不能只因为定时执行就叫「深度」，应通过以下能力体现：

- 比持续采集更高的采样频率（持续 19Hz、深度诊断 99Hz）
- 使用更完整的调用栈（如 DWARF）
- 支持 Java `cpu/wall/alloc`
- 支持 Go CPU/Heap pprof
- 支持专项 eBPF IO、调度诊断
- 每个窗口保留完整、独立的诊断产物
- 运行相对昂贵的离线分析和基线 Diff

> 持续采集追求低成本覆盖；周期性采样追求有限时间内看得更清楚。

## 7. 推荐的默认效果（稀疏高保真）

不要默认「每 5 分钟采 290 秒」——这会退化成不稳定的伪持续采集。建议稀疏、高保真预设：

| 场景 | 周期 | 每次采集 | 建议频率 |
|---|---:|---:|---:|
| 高频巡检 | 每 5 分钟 | 30 秒 | 99Hz |
| 常规巡检 | 每 15 分钟 | 60 秒 | 99Hz |
| 低频基线 | 每小时 | 120 秒 | 99Hz |
| 高峰诊断 | 每天指定时间 | 3～5 分钟 | 按采集器配置 |

创建时展示预计占空比与风险提示，例如：

> 每 5 分钟采集 30 秒，采集占空比 10%。适合高频性能巡检。

占空比过高时提示：

> 当前计划 80% 的时间都在采集，更适合使用持续观测。

## 8. 页面定位与命名

入口命名建议：

- 立即诊断
- 新建定时诊断
- 开启持续观测

周期计划详情页命名建议：

> 定时深度诊断：API 高峰巡检

创建页重点配置顺序：

1. 目标服务或进程
2. 诊断类型
3. 触发时间
4. 每次采集时长
5. 深度参数
6. 基线和异常规则

Cron 放高级配置，普通用户优先使用「每 5 分钟」「工作日 10:00」「每天高峰期」等自然选项。

## 9. 最重要的差异化功能

让周期性采样真正有保留价值，至少具备：

- 自动与上一窗口比较
- 与昨天同一时刻比较
- 设置发布前基线
- 标出新增、消失、变热、变冷的热点
- 连续多个窗口异常时提示性能回归
- 计划失败、目标进程消失时明确告警
- 按 exe 或服务跟随进程重启，而非长期绑定旧 PID

## 10. 最终产品定义

> 定时深度诊断面向可预测、重复发生的性能问题，在指定时间自动运行高保真采集器，为每次执行生成独立诊断报告，并通过时间轴、基线对比和回归检测发现热点变化。

核心价值不是「周期」，而是三个词：**自动执行、高保真、可比较**。

## 11. 现状对照（代码证据）

### 11.1 定位已天然契合

`docs/design.md` 第 195–203 行已写明，与本文定位逐字吻合：

```text
schedule_task -> cron trigger -> child hotmethod_task -> normal task flow
```

每次 cron 触发创建一个普通 `HotmethodTask`，`master_task_tid` 指向定时任务 SID。所以「与单次采样共用采集器/任务/产物/分析链路，只是触发方式不同」在代码里已是事实，非待改造目标。

### 11.2 「深度」方向反了

看 `web_frontend/src/components/CreateTaskModal.js` 默认参数：

| 场景 | 默认 frequency | 默认 duration | 出处 |
|---|---|---|---|
| 单次采样 | **99Hz** | 10s | `CreateTaskModal.js:111` |
| 周期预设 | **19Hz** | 290s / 50s / 580s / 1740s | `CreateTaskModal.js:41-44`（`WINDOW_PRESETS`） |

两个问题：

1. **默认预设即反例**：`5 分钟窗口(默认) duration=290`，即「每 5 分钟采 290 秒」，占空比 97%，是不稳定的伪持续采集。
2. **周期采样比单次采样更低保真**：周期预设 19Hz、单次默认 99Hz。本文主张「持续 19Hz / 深度 99Hz」，当前实现把关系倒过来了——周期采样退回持续采集的频率，丢掉了「有限时间内看得更清楚」的深度定位。

采集器能力本身已齐备（`docs/design.md:174-179`：perf / async-profiler Java / pprof Go / eBPF），但周期预设未启用 99Hz 深度通道。

### 11.3 差异化功能差距清单

| 本文主张的能力 | 现状 | 位置 |
|---|---|---|
| 与上一窗口自动比较 | 无，需手动「设为基线」+「与基线对比」 | `ScheduleTimeline.js` |
| 与昨天同一时刻比较 | 无 | — |
| 发布前基线 | 有等价物（手动「设为基线」星标） | `ScheduleTimeline.js:315-328` |
| 标出新增/消失/变热/变冷 | 部分有（红=更热 / 绿=更冷） | `TaskDiffPage.js` |

| 计划失败/进程消失告警 | 有状态徽章 + `DropAgentNotice`，无「进程消失」专项告警 | `HostDetailPage.js` |
| 按 exe 跟随进程重启 | 持续采集有 `selector_exe`，周期采样无此概念 | `ContinuousProfilingPanel.js` |

## 12. 技术风险与开销分析

### 12.1 定时 + 高保真结合的四个问题

1. **时间窗口错位（最致命）**：cron 是死的、负载是活的。生产高峰会漂移（可能 10:03 而非精确 10:00）。定时采集若与真实异常窗口错开几分钟，采到的就是正常时段 profile，诊断失效。持续采集靠全覆盖 + 事后回溯，无需「赌对时刻」。
2. **高保真开销脉冲叠加在高峰**：深度诊断想采的时段恰是系统最忙的时段。99Hz + DWARF 展开在窗口内产生 CPU 开销尖峰，叠加高负载会放大延迟、污染样本（采集器自身 CPU 落入 profile 形成自采样伪影）、极端时影响业务。
3. **短窗口样本量瓶颈**：99Hz × 60s = 5940 样本，占比 1% 的函数仅 ~60 个样本，噪声大。持续采集虽 19Hz 但全天累积可聚合巨量样本，统计更稳。「短时高保真」赢解析度、「长时间聚合」赢置信度，不可兼得。
4. **调度与目标进程脆弱性**：依赖调度器可靠、时钟准确、目标进程在采集时刻存活且 PID 未变。进程重启旧 PID 失效 → 空采或采错；进程未起 → 白跑。持续采集 agent 常驻 + 自动发现进程天然免疫。

### 12.2 持续采集 + 高保真的开销：分时 vs 叠加

| 环节 | 开销 |
|---|---|
| CPU 采样 99Hz（frame-pointer 展开） | <1% |
| CPU 采样 99Hz（DWARF 展开） | 明显上升，展开 ~5μs/次 vs frame-pointer ~0.5μs/次，贵约一个数量级 |
| 符号化 / 火焰图 / diff / 分析 | 比采样贵，但可离线异步 |
| 高保真原始产物存储 | 体积大，随深度窗口数量线性膨胀 |

- **叠加（反模式）**：两个 profiler 在同一进程注册采样信号/PMU 中断会互相干扰，且开销不止加总。
- **分时/错峰（正确做法）**：深度窗口稀疏（每天 4 次 × 60s = 4 分钟，占空比 0.046%）。平时持续 19Hz 覆盖，深度窗口期间要么同一 profiler 临时调速到 99Hz，要么独立 `perf record -F 99 --call-graph dwarf` 与持续采集错开；昂贵环节（符号化/diff/分析）全部离线异步。总开销 = 持续 <1% + 稀疏窗口短期脉冲，可控。业内实践：CPU profiling 持续跑、内存/off-CPU profiling 按需开启，本质即「持续低开销 + 按需高保真」。

### 12.3 三个硬约束

「定时深度诊断」工程上成立，但有三个硬约束：

1. **稀疏**：占空比必须极低（分钟级/天），否则退回伪持续采集。
2. **错峰或复用**：深度窗口不能与持续采集简单叠加，要么调速复用同一采样器，要么错开资源。
3. **离线化**：符号化 + diff + 分析异步执行，不压业务节点。

这解释了为何业内没有「定时深度诊断」独立形态：它同时继承「定时错位」的脆弱性与「高保真开销脉冲」的代价，只换来「可比较」一个好处，而该好处持续采集 + diff 已用更省心的方式拿到。mini-drop 要立住，须把上述三个约束解决得比「持续采集 + 事后选窗 diff」更省心。

## 13. 业内对标调研

### 13.1 主流形态：持续剖析 + 差分火焰图

业内没有「定时深度诊断」独立产品形态，主流是 **Continuous Profiling（持续剖析，可观测性「第四支柱」）+ 差分火焰图**：

| 工具 | 采集方式 | 时间窗 Diff | 回归检测/告警 | 定时采集 |
|---|---|---|---|---|
| Grafana Pyroscope | SDK push + eBPF pull | ✅ diff 火焰图（对比两时间范围/版本） | ✅ Grafana 告警 | ❌ |
| Parca（Polar Signals） | eBPF-only | ✅ 招牌 version diff（红=回归/蓝=改善） | 弱 | ❌ |
| Blackfire | 持续剖析 | ✅ A/B 时间窗（红=增/绿=减/灰=单侧） | 部分 | ❌ |
| AWS CodeGuru Profiler | Java/Python 托管 | ✅ 对比基线期 | ✅ 自动异常检测 + 邮件告警 | ❌ |
| Google Cloud Profiler | 托管 | 较弱 | 弱 | ❌ |

它们用「持续全覆盖 + 事后任选时间窗 diff」消解了「定时」。持续采集默认是低频采样——Parca 官方默认 19Hz（选质数避免与机器周期性事件锁步）、Pyroscope eBPF 同样低频，深度靠「全量保留 + 时间聚合 + 事后 diff」而非高采样率；99Hz + DWARF 是 ad-hoc 深度诊断（`perf record -F 99`）的标准，不是持续采集的标准。差分火焰图配色惯例为红=变热/蓝=变冷（Brendan Gregg `difffolded.pl` 沿用至今），mini-drop 当前用绿=变冷（Blackfire 约定），若对齐主流建议改红/蓝。

### 13.2 检测驱动诊断的业内落点

三形态协同在业内的落点：

| 形态 | 业内对应 | 成熟度 |
|---|---|---|
| 持续采集（哨兵） | Datadog Continuous Profiler / Pyroscope / Parca | 成熟 |
| 自动检测 | Datadog Automated Analysis、YugabyteDB Performance Advisor | 成熟 |
| 检测→触发深度诊断 | 阿里云 SysOM 一键 I/O 诊断（唯一接近） | 罕见，通用场景空白 |
| 定时诊断（预置） | 无独立产品 | 空白 |

两个标杆：

- **Datadog Automated Analysis**（检测环标杆）：在持续 profiler 数据上自动跑几十种 insight 规则，检测到即给诊断结论 + 建议 + 自动生成修复。规则覆盖 CPU Burst（10s >75%）、High Lock Contention、Deadlocked Threads、GC Pauses、Allocation Stall 等——与 mini-drop 设想的 db lock_wait/slow query 检测高度同构。注意：它检测后不触发额外采集，直接从已有的持续 profile 数据 diff 出答案。
- **阿里云 SysOM 一键 I/O 诊断**（触发环罕见先例）：明确表述为 "monitor-first, on-demand capture"——周期读指标 → 三层动态阈值（base 滑动窗口 + compensation 补偿 + static 静态最小）→ 超阈值自动触发子诊断工具（带频控）→ 结构化报告。但局限 I/O 专项、触发的是诊断工具而非更高保真采样器。

### 13.3 SysOM 检测→触发诊断的实现拆解（落地参考）

SysOM-ai 是阿里云 SysOM 的 AI 工具集（MCP Server + Agent Skills），其巡检技能 `alibabacloud-sysom-inspection` 完整实现了「检测→触发深度诊断」闭环，可作为 mini-drop 该环节的最小实现范本。

**闭环流程**（`skills/alibabacloud-sysom-inspection/scripts/sysom_cli/inspection/command.py`）：

```text
巡检 19 个 sysom:metric:* 指标
  → CreateInstanceInspection（服务端巡检）
  → GetInspectionReport（读巡检报告）
  → _has_memory_usage_issue：报告命中 memory_usage_rate 且状态 abnormal/alert/critical/异常/告警？
        ├─ 是 → InvokeDiagnosis(memgraph) 触发深度诊断
        └─ 否 → 跳过
  → GetDiagnosisResult 轮询（间隔 1s，超时 150s，直到 success/fail）
```

**关键设计**：

1. **触发条件极简**：`MEMORY_USAGE_ITEM = "sysom:metric:memory_usage_rate"`（command.py:20）——只做「内存使用率异常 → memgraph」这一个显式映射，不是通用智能引擎。
2. **触发带溯源**（`_invoke_memgraph_diagnosis`）：params 注入 `trigger_item` + `trigger_report_id` + `__sysom_diagnosis_source=skill_hub`，完整记录触发原因与来源。
3. **幂等/频控**：`clientToken` sha256 哈希去重 + `--disable-memgraph-diagnosis` 开关 + 轮询超时。
4. **决策在服务端**（SKILL.md）：阈值/规则判定在服务端巡检报告里，客户端只做「读报告 → 看 abnormal → 触发诊断」的编排，不做本地阈值。

**对 mini-drop 的映射**：

| SysOM 概念 | mini-drop 对应 |
|---|---|
| 巡检指标 `sysom:metric:*`（19 项） | 持续采集信号（cpu/io/io_syscall/sched/db）+ 热点 diff |
| 巡检报告（服务端标好 abnormal） | 持续采集分析结果（哪些指标异常/函数变热） |
| 触发条件 `memory_usage_rate` | 检测规则：CPU 突增 / 锁等待增多 / 热点变热 |
| `InvokeDiagnosis` memgraph | 触发一次 99Hz 深度诊断任务 |
| `GetDiagnosisResult` 轮询 | 深度诊断任务状态机（mini-drop 已有） |
| `trigger_item` + `trigger_report_id` | 诊断任务溯源（区分检测/手动/定时来源） |
| `clientToken` 幂等 | 同异常冷却，避免重复触发 |

**三个可复用的设计模式**：

1. 检测与触发解耦，决策在服务端
2. 触发动作带溯源
3. 显式稀疏映射（指标 → 诊断规则表），不搞通用智能引擎

### 13.4 差异化：触发换深度 vs 时间聚合换深度

「检测→触发更高保真采集」业内几乎没人做，原因需要精确化：业内持续采集**本身也是 19Hz 低频**（Parca 官方默认 19Hz，选质数避免锁步），并非高保真。它们用「全量保留 + 时间聚合 + 事后 diff」来补深度——把长时间的低频样本攒起来做统计对比，抓的是「缓慢漂移的回归」（今天某函数比昨天多了 5% CPU）。

这套时间聚合的局限在于：19Hz 采不到瞬时高频细节——一个只持续 1 秒的 CPU 尖峰，19Hz 只能采到十几个样本，分辨率不够。而 mini-drop 的「触发深度诊断」恰好补这个空：

| | 深度从哪来 | 适合什么 |
|---|---|---|
| 业内（Parca/Pyroscope） | 时间聚合：全量保留 + 事后 diff | 缓慢漂移的回归 |
| mini-drop 设想 | 触发换深度：哨兵抓到苗头后临时拉高 99Hz + DWARF | 瞬时尖峰、高频事件的精确解剖 |

所以差异化不是「低频 vs 高频」（业内持续采集也是低频），而是「**时间聚合换深度 vs 触发换深度**」——两者解决不同的问题。这也是为什么「检测→触发」这个动作在业内被「事后 diff」取代了：对持续型回归，时间聚合已足够；只有对瞬时高频细节，触发 99Hz 才有增量价值。

mini-drop 的差异化若要成立，就必须把「触发 99Hz 深度诊断」的价值精准落在「瞬时尖峰 / DWARF 完整栈解剖」上，而不是笼统的「更高保真」；且成败押在「检测准不准」——哨兵若误报，反而把平时省下的开销又花回去。

## 14. 落地路径（三层）

按成本从低到高：

1. **产品定位与命名**：改文案与命名（入口「立即诊断 / 新建定时诊断 / 开启持续观测」，详情页「定时深度诊断」），不涉及逻辑改动。
2. **默认预设修正**：改 `WINDOW_PRESETS` 为稀疏高保真（30s/60s/120s @ 99Hz），并在创建页展示占空比与风险提示。成本最低、收益最大。
3. **差异化能力**：自动与上一窗口/昨天同时刻比较、连续窗口回归告警、按 exe 跟随进程重启。

验收标准：周期采样是否合格，看是否做到「自动执行 + 高保真 + 可比较」三件事。当前「自动执行」已做到，「高保真」做反了（19Hz 而非 99Hz），「可比较」只做了手动一半。
