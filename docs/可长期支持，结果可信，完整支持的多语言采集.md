要实现“可长期运行、结果可信、完整支持 Native/Go/Java/Node/Python 的最终版”，建议按下面顺序推进。不要先从 `analysis/flamegraph.py` 开始；Continuous 主链路并不经过它。第一优先级应是数据正确性和 strict 主链路统一。

## 一、先冻结最终版范围

建议最终版明确交付以下能力：

- 持续 CPU：Native、Go、Java、Node.js、Python。
- 持续指标：IO、syscall IO、调度延迟。
- 内存：
  - Python RSS；
  - Python Memray 显式接入；
  - Go Heap 继续采用按需 pprof。
- Scope：
  - host；
  - 单一 PID instance；
  - exe all-instances；
  - 后续扩展 cgroup/container。
- 数据保证：
  - 窗口不重复；
  - 不丢失已确认窗口；
  - 用户没选的 signal 不采集、不存储；
  - runtime、symbol status 真实可信。
- 查询：
  - 火焰图、TopN、diff、语言筛选、进程筛选；
  - coverage、ingest lag、真实 gap 分开显示。
- 运维：
  - 低磁盘背压；
  - Agent 重启恢复；
  - 进程重启跟随；
  - 版本和 capability 可观测。

最终版暂不承诺 Ruby/PHP/.NET 的语言级栈，它们先明确显示为 `native fallback`。

# 阶段 1：先修数据正确性

这是所有多语言工作之前的 P0。

## 1.1 修复 signals 被忽略

当前 `ContinuousSessionManager::BuildSamplerConfig()` 硬编码：

```cpp
samplerConfig.signals = "cpu,io,io_syscall,sched";
```

需要：

1. 在 `ContinuousAssignment` 中保存服务端下发的 signals。
2. `ParseAssignments()` 正确解析 base64/json signals。
3. `BuildSamplerConfig()` 按 Session 生成真实 signals。
4. 共享物理采集器取所有 Session signals 的并集。
5. fan-out 时，每个 Session 再按自己的 signals 过滤。
6. 不生成未请求的 histogram/profile/metric。
7. CPU、latency、memory 的 sample count 分开统计。

重点文件：

- `drop/agent/ContinuousSessionManager.*`
- `drop/common/ContinuousSampler.*`
- `apiserver/server/continuous_control.go`
- `apiserver/server/continuous.go`

验收：

- 只请求 `cpu_profile` 的 Session，数据库只能出现 CPU window；
- Java/Node/Python Session 不再收到未请求的 IO/sched；
- batch 的 signal_types 与创建请求严格一致。

## 1.2 建立真正的窗口幂等

不能再依靠 batch ID conflict 后简单 re-key。

定义稳定窗口身份：

```text
session_sid
+ collector_generation
+ window_start
+ window_end
+ signal_type
+ target_identity
+ content_hash
```

需要：

1. Agent 给每次 shared engine 启动生成 `collector_generation`。
2. 每个物理 segment 生成稳定 `segment_id`。
3. fan-out 后生成稳定 `window_id`。
4. 数据库为 `window_id` 建唯一约束。
5. batch 重试保持原 ID，不能随意换 ID。
6. 同一内容重复上传返回 duplicate ACK。
7. 相同 ID、不同内容才属于真正 conflict。
8. conflict 进入 quarantine，不直接 re-key 接收。
9. 查询层临时增加去重保护，防止历史重复窗口双计数。
10. 编写历史重复数据检查和修复脚本。

重点文件：

- `ContinuousSampler.cpp` spool/batch 逻辑；
- `continuous.go` ingest；
- `profile_batches`、`profile_windows` 模型；
- 新数据库 migration；
- `migration_receipts`、`coverage` 相关代码。

验收：

- Agent 重启、PID 变化、网络重试、API 500 后都不产生重复窗口；
- 蓝绿切换 100 次，数据库重复窗口为 0；
- 同一 payload 重传得到 duplicate ACK，不新增记录。

## 1.3 修正 coverage 语义

需要区分：

- `confirmed_coverage`：服务端已经收到的数据；
- `pending_tail`：仍在 upload batch 延迟内；
- `ingest_lag`：event time 到 received time；
- `real_gap`：超过合理延迟仍无数据；
- `collector_restart_gap`；
- `target_idle`：进程存在但没有 CPU 样本。

重点文件：

- `apiserver/server/coverage.go`
- `continuous.go`
- Timeline 前端页面。

验收：

- 正常 40 秒 upload batch 不再被显示为 40 秒采集缺口；
- 只有超过 `upload_batch_sec + grace` 才判定 real gap。

# 阶段 2：统一 strict 和 degraded 的采集流水线

这是多语言能力的核心。

当前：

```text
degraded collect_window
  有 runtime map / GoReSym / py-spy / RSS / Memray

strict RollingPerfRecorder::Drain
  只有 perf script
```

需要改成统一的 segment enrichment：

```text
RollingPerfRecorder
  → immutable perf segment
  → discover sampled processes
  → prepare symbols/runtime maps
  → perf script
  → normalize samples
  → language fallback
  → diagnostics
  → per-session fan-out
```

建议抽象：

```cpp
class ContinuousSegmentProcessor {
    ProcessResult Process(
        PerfSegment segment,
        PhysicalTargetSet targets,
        RuntimeCapabilitySet capabilities);
};
```

职责：

1. `warm_build_id_cache()`；
2. kernel symbols；
3. `collect_runtime_maps()`；
4. `prepare_go_symbols()`；
5. Python fallback 调度；
6. `perf script`；
7. runtime 分类；
8. structured frames；
9. unresolved 统计；
10. 生成物理层 diagnostics。

strict 和 degraded 都调用它，避免两套能力再次分叉。

重点文件：

- `drop/common/ContinuousSampler.cpp`
- `RuntimeSymbolMap.*`
- `GoSymbolizer.*`
- `PythonRuntimeProfiler.*`
- `BuildId.*`

验收：

- strict Python/Java/Node/Go 都会生成 `symbol_refs`；
- strict 与 degraded 对同一个 perf.data 的解析结果基本一致；
- 生产环境进入 strict 后不会失去语言能力。

# 阶段 3：正确处理共享采集和 Session fan-out

物理诊断不能直接复制，也不能全部清空。

需要定义两层数据：

## 物理层

包含：

- 所有采样 PID；
- 所有 runtime maps；
- 所有 symbol refs；
- 物理 backend 状态；
- lost events；
- recorder generation。

## Session 层

按以下身份过滤：

```text
PID + process_start_ms + exe
```

并生成 Session 专属：

- samples；
- profiles；
- metrics；
- histograms；
- symbol refs；
- runtime diagnostics；
- unresolved statistics。

需要移除：

```cpp
out.symbolRefsJson.clear();
```

改成结构化过滤。

验收：

- 多个 process Session 同时运行时看不到其他 selector 的 PID、路径和诊断；
- 每个 Session 都保留自己的 symbol refs；
- 一个 Java Session 的 map 状态不会出现在 Node Session。

# 阶段 4：逐语言完成适配

## 4.1 Native

需要：

- build-id store；
- ELF/DWARF symbol store；
- kernel kallsyms；
- stripped binary 的明确诊断；
- 容器内 DSO 路径解析；
- deleted mapping 支持；
- frame-pointer/DWARF 策略。

验收目标：

- 自有未裁剪 Native 服务未解析率低于 5%；
- stripped binary 明确显示缺少哪个 build-id，而不是泛化为 partial。

## 4.2 Go

修复 runtime 识别：

1. Go build-info；
2. Go pclntab；
3. 明显的 `runtime.*`、模块函数作为结果级辅助判断；
4. 不能只依赖 exe 名称。
5. strict 路径接入 GoReSym。
6. GoReSym 仅作为 stripped Go fallback，避免每窗重复提取。
7. cache 状态进入 diagnostics。

验收：

- dockerd 必须标成 `go`；
- `runtime=go` 筛选能返回样本；
- stripped Go 测试程序仍可显示业务函数；
- GoReSym pending/ready/failed 状态真实显示。

## 4.3 Java

将已有 asprof perf-map 刷新正式接进 strict：

- 新 JVM 首窗自动生成 map；
- 60 秒刷新冷却；
- JVM 数量上限；
- attach timeout；
- PID/start-time 校验；
- map 原子更新；
- attach 权限错误显示明确原因；
- map 生成失败时不能显示 ready。

验收：

- 无需用户手工运行 asprof；
- Java 业务方法在首个或第二个窗口出现；
- `[未解析] perf-<pid>.map` 不再成为主要热点；
- JIT 新方法在后续窗口能被刷新。

## 4.4 Node.js

支持两种状态：

- `--perf-basic-prof` map ready；
- map missing，给出明确启动参数提示。

需要：

- map mtime/start-time 校验；
- PID namespace 路径处理；
- stale map 清理；
- JIT map 变化检测；
- JS frame coverage 指标。

验收：

- `LazyCompile`/JS 函数可以过滤和展示；
- 未带启动参数的 Node 显示 `missing --perf-basic-prof`，而不是 ready。

## 4.5 Python

建议形成两级策略：

### 优先级一：Python 3.12+ `-X perf`

- 检查真实 perf-map；
- 检查 Python semantic frame coverage；
- 不只是检查文件是否存在。

### 优先级二：py-spy fallback

触发条件：

- 无 perf-map；
- Python 版本不支持；
- Python semantic frame coverage 低于阈值；
- interpreter/native frame 占比过高。

需要改进：

- 首窗就能根据进程版本和启动参数决定 fallback，不等上一窗口；
- process Session 只采目标 PID；
- host Session 对 Python 进程按 CPU 热度限流；
- py-spy 结果与 perf native 栈分轨或明确标注来源，避免重复计数。

验收：

- 纯 Python负载能直接定位业务函数；
- Python 3.10 自动走 py-spy；
- Python 3.12 `-X perf` 正常走 perf-map；
- C 扩展负载同时显示 Python 调用入口和 native C 热点。

# 阶段 5：重新设计语言状态和符号状态

不要再把“有样本”叫 ready。

建议状态拆分：

```json
{
  "runtime_detection": "detected",
  "collector_mode": "perf-map|py-spy|goresym|native",
  "collector_status": "ready|partial|missing|failed",
  "symbol_status": "complete|partial|missing|unknown",
  "semantic_frame_percent": 92.4,
  "unresolved_frame_percent": 4.1,
  "sample_count": 1234,
  "reasons": []
}
```

规则示例：

- 有样本但没 Java perf-map：`detected + missing`；
- 有 Node map但未解析率 42%：`partial`；
- 没有 symbol refs：`unknown`，不能是 complete；
- GoReSym 后台处理中：`pending`；
- Python py-spy 达到覆盖阈值：`ready`。

需要修复无条件创建 Python诊断项的问题。

验收：

- 非 Python Session 不再显示虚假的 Python 行；
- flamegraph partial 与 symbol-check 结果一致；
- UI 每个状态都提供可执行的修复建议。

# 阶段 6：完善 selector 模型

当前只有：

```text
exe + all_instances
```

最终至少支持：

1. `pid_instance`
   - PID；
   - process_start_ms；
2. `exe_all_instances`；
3. `cgroup`；
4. `container_id`；
5. 可选 systemd unit。

默认创建 process Session 时建议选择一个具体 process instance，而不是自动包含所有同路径进程。

进程退出策略：

- `pid_instance`：进入 waiting，不自动跟随同路径新 PID；
- `exe_all_instances`：自动跟随新实例；
- cgroup/container：跟随组内进程变化。

验收：

- 用户选择 Python业务进程时不会采到系统升级服务；
- PID 复用不会把新进程算进旧 instance；
- 进程重启是否跟随由 selector mode 明确决定。

# 阶段 7：完成内存产品

## Python RSS

RSS 应独立于 CPU backend：

- strict 和 degraded 都能采；
- host/process scope 都支持；
- process Session 只采目标；
- RSS 采集失败要有诊断；
- UI 不再说“仍可查询”但返回空。

## Memray

明确它是显式 SDK/文件 ingest，不是透明 attach：

- SDK 接入状态；
- profile 完整性；
- profile ID 幂等；
- 不重复消费同一个 Memray profile；
- 与 CPU 时间范围关联。

## Go Heap

继续使用按需 pprof，但在 Continuous Memory 页面提供统一跳转和关联：

- 当前时间范围；
- 对应目标；
- 最近 heap task；
- CPU 与 heap 结果关联。

```text
相同时间范围 + 相同 filters
→ flamegraph total
→ TopN total
→ diff 输入 total
→ raw aggregate total
```

必须一致。

# 阶段 10：压力、故障和安全验收

至少运行以下测试：

## 长稳

- 5 个语言 Session 并行运行 24 小时；
- Agent RSS 无持续增长；
- spool 无异常增长；
- 数据延迟稳定；
- 无 batch conflict；
- 无重复窗口。

## 故障

- 重启 Agent；
- 重启 API；
- MinIO 暂停；
- Postgres 短暂不可用；
- 网络断开；
- 磁盘低水位；
- 目标进程重启；
- PID 复用；
- Java attach 拒绝；
- perf-map 被删除或截断。

## 性能

目标建议：

- 19Hz 持续 CPU Agent 平均开销小于 1%～2%；
- runtime enrichment 不阻塞 recorder；
- perf segment 处理速度持续快于生成速度；
- ingest lag 正常低于 `2 × upload_batch_sec`；
- CPU 高负载下不产生无限 backlog。

## 安全

- 不上传业务绝对源码路径；
- 不上传命令行敏感参数；
- 不跨用户读取不授权进程；
- symbol map 进行 PID/start-time 校验；
- Java/py-spy attach 可配置禁用；
- selector 遵守租户和主机权限。
